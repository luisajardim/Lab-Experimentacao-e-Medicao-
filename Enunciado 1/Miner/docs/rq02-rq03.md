# RQ02 e RQ03 — pull requests aceitas e releases

## 1. Hipóteses informais (escritas antes de olhar os dados coletados)

**RQ02 — Sistemas populares recebem muita contribuição externa?**
Hipótese: sim. Repositórios com muitas estrelas tendem a ter uma comunidade maior
e mais visibilidade, o que deve atrair contribuições na forma de pull requests.
Assim, espero que a maior parte dos repositórios populares possua uma quantidade
relevante de PRs aceitas, embora alguns projetos muito grandes possam concentrar
valores excepcionalmente altos.

**RQ03 — Sistemas populares lançam releases com frequência?**
Hipótese: sim, para uma parcela expressiva. Projetos populares normalmente
precisam comunicar versões, correções e novas funcionalidades aos usuários, então
espero encontrar um histórico relevante de releases. Porém, espero também que
alguns repositórios não usem a funcionalidade Releases do GitHub — por exemplo,
projetos que distribuem versões apenas por tags, pacotes ou imagens de contêiner.

## 2. Extração e cálculo

Spec usada: [`specs/github-rq2-rq3-v2.yaml`](../specs/github-rq2-rq3-v2.yaml).
Ela busca `nameWithOwner`, `primaryLanguage.name`, o total de pull requests com
estado `MERGED` e o total de releases dos 1.000 repositórios ordenados por
estrelas.

O exportador padroniza os campos no CSV gerado:

- **RQ02 — `total_pr_aceitas`**: `pullRequests(states: MERGED).totalCount`;
- **RQ03 — `total_releases`**: `releases.totalCount`;
- valores nulos, ausentes ou inválidos em métricas numéricas são exportados como
  `0`, e as contagens são garantidas como inteiros não negativos;
- `data_coleta` registra o instante da coleta para rastreabilidade.

Para rodar:

```bash
npm run dev -- ./specs/github-rq2-rq3-v2.yaml
```

O CSV é salvo em `data/github-rq2-rq3-v2_<timestamp>.csv`.

## 3. Validação de consistência e outliers

A auditoria foi executada sobre 1.000 registros do CSV coletado. O relatório
completo está em [auditoria_rq02_rq03.md](./auditoria_rq02_rq03.md) e pode ser
regenerado com:

```bash
npm run audit:rq02-rq03
```

| Verificação | Resultado |
|---|---:|
| Registros válidos | 1.000 |
| Valores inválidos em `total_pr_aceitas` | 0 |
| Valores inválidos em `total_releases` | 0 |
| Nomes de repositório duplicados | 0 |
| Repositórios com zero releases | 286 (28,60%) |
| Mediana de PRs aceitas | 768 |
| Mediana de releases | 39 |

Foram usados quartis e o critério de Tukey (`Q3 + 1,5 × IQR`) para identificar
outliers. Foram encontrados 124 outliers de PRs aceitas e 93 de releases. Eles
foram mantidos no conjunto, pois representam repositórios reais; na análise da
Sprint 3, a mediana deve ser priorizada em relação à média, que é mais sensível
a esses valores extremos.

## 4. Registro de limitações e discrepâncias

- Não foram encontrados campos numéricos inválidos, valores negativos, nomes
  duplicados, `null`, `undefined` ou `NaN` no CSV auditado.
- Repositórios com `total_releases = 0` não são erros de extração. Eles podem não
  publicar releases pela interface do GitHub, mesmo que distribuam versões por
  outros meios.
- A métrica de RQ02 mede PRs aceitas, mas não distingue contribuições externas
  de PRs feitos por mantenedores, membros da organização ou bots. Assim, ela é a
  aproximação exigida pelo enunciado, não uma prova isolada de contribuição
  externa.
- O total histórico de releases não mede frequência diretamente: repositórios
  mais antigos tiveram mais tempo para acumular lançamentos. Essa limitação deve
  ser considerada na discussão dos resultados.
